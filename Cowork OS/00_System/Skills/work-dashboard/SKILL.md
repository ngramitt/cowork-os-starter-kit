# Work Dashboard

Last updated: 2026-09-28 (living document; Cowork OS Starter Kit v1.0)

## What this is

A deterministic roll-up of every workstation's MEMORY.md "Current Status"
section into one root-level `DASHBOARD.md`, grouped Active / Dormant / Closed
(Dormant = no MEMORY.md update in 60+ days, or an override in `lifecycle.txt`).
It makes the OS's biggest blind spot ("what's going on across every
workstation?") a one-file read, and it
doubles as a nag list: a wrong or bloated status on the dashboard is a
prompt to fix that workstation's MEMORY.md.

## When to run

- The owner asks for a status overview, what's active, or what to focus on.
- End of any session that updated a MEMORY.md Current Status (keeps the dashboard from silently rotting).
- Start of a planning/review session.

## Procedure

1. Run:

   ```
   python3 -B "00_System/Skills/work-dashboard/scripts/dashboard.py" "<workspace root>"
   ```

   (`--stdout` previews without writing; `--full` prints every Current
   Status in full.)

   The default is one table row per workstation, grouped
   **Active / Dormant / Closed**. The row shows the status's "Next action"
   (or its first sentence) and a ⚠ when Current Status is over the 80-word
   budget. **Dormant** = no MEMORY.md update in 60+ days, or marked dormant
   in `lifecycle.txt` next to this file; **Closed** = marked closed there.
   An **Open tasks** column counts the unchecked items under Active in the
   workstation's `Tracking/Tasks.md` (— when it has none), so the task
   lists stay visible. The date is
   the owner's local date (from `00_System/workspace-config.txt`). Change `lifecycle.txt` only on the owner's word. Marking a workstation closed
   archives nothing by itself: memory archiving still follows the
   memory-maintenance skill, and the folder stays put.
2. Skim the output for statuses that are stale, wrong, or bloated. The fix
   is ALWAYS in the source: edit that workstation's MEMORY.md Current
   Status (state, blocker, next action, as of; 80 words or fewer),
   then re-run. Never hand-edit DASHBOARD.md.
3. If a Dormant workstation is actually done, that's a memory-maintenance
   trigger (archive to ARCHIVE.md — with the owner's confirmation).

## Without Python

Answer "what's on my plate?" straight from the sources: each workstation's `MEMORY.md` Current Status (its next action) and each `Tracking/Tasks.md` (unchecked items under Active). Then refresh `DASHBOARD.md` by hand in the same shape the script writes. Keep the AUTO-GENERATED marker line at the top, because a later Python run replaces the file.

```
<!-- AUTO-GENERATED by 00_System/Skills/work-dashboard — do not hand-edit; re-run dashboard.py instead. -->

# Active Work Dashboard — YYYY-MM-DD

## Active (N)

| Workstation | Updated | Open tasks | Where it stands |
| --- | --- | --- | --- |
| Name (or Parent → Area) | 0d ago | 2 | Next: <the Current Status next action> |

## Dormant (0)

_None._

## Closed (0)

_None._
```

"Updated" is days since that `MEMORY.md` last changed. "Open tasks" is the count of `- [ ]` lines under `## Active` in its `Tasks.md` (— if it has none). A by-hand refresh is the one sanctioned exception to "never hand-edit."

## Safety

`DASHBOARD.md` is the only file the script writes, and it refuses to
overwrite any file lacking its AUTO-GENERATED marker. The file is
machine-regenerable by definition — regenerating it is not an "overwrite"
in the sense of the owner's confirm-first rule (that's its documented contract).

## Editing this skill

The thresholds (`DORMANT_DAYS = 60`, `STATUS_WORD_BUDGET = 80`, and the
`--full` layout's `stale_cut = 21`) and the marker text live in
`scripts/dashboard.py`; lifecycle overrides live in `lifecycle.txt`.
